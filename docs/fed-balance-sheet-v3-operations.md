# FedBalanceSheet v3 사내 운영 작업 명세

매일 한국시간 오전 7시 15분에 v3에 필요한 전체 이력을 수집한다. 화면에 표시할 데이터가 바뀐 경우에만 새 JSON을 4,000바이트 이하의 조각으로 나눠 Altibase에 저장한다. 새 버전 검증이 끝나면 화면이 읽는 버전을 한 번에 전환한다.

최종 운영 화면은 [FedBalanceSheet_v3.html](../FedBalanceSheet_v3.html)이다. 회사 웹서버는 Altibase에 저장된 조각을 합쳐 기존 화면이 받는 JSON 구조로 전달한다.

## 1. 수집 일정과 범위

- **실행 시각**은 매일 오전 **07:15 KST**로 고정한다. 주말과 공휴일에도 같은 시각에 확인한다. H.4.1의 새 주간 자료는 통상 한국 금요일 아침에 반영된다.
- **전체 이력**은 아래 시작일부터 수집 시점에 공개된 최신 자료까지를 뜻한다. 날짜를 지정하는 원천은 여러 구간으로 나눠 받아도 되지만, 해당 범위 전체를 확인한 뒤 결과를 만든다.
- SOFR와 EFFR은 기존 v3보다 과거 금리 이력을 확대한다. IORB와의 금리 차이는 같은 날짜에 두 값이 모두 있는 경우에만 계산한다.

| 원천 | 매일 수집할 범위 | v3 반영 기준 |
|---|---|---|
| **H.4.1 연준 대차대조표** | 연준이 제공하는 전체 XML 파일 | 주간 통합 화면은 **2013-09-25**부터 수요일 잔액 사용 |
| **ON RRP 익일물 역레포** | **2013-09-23**부터 최신 공개 거래일까지 | H.4.1 관측일과 같은 수요일 거래 결과를 연결 |
| **SOFR 담보부 익일물 금리** | **2018-04-02**부터 최신 공개 관측일까지 | 일간 금리 이력을 보존하고 주간 화면에는 같은 수요일 값 사용 |
| **EFFR 실효 연방기금금리** | **2013-09-25**부터 최신 공개 관측일까지 | 일간 금리 이력을 보존하고 주간 화면에는 같은 수요일 값 사용 |
| **IORB 지급준비금 이자율** | 연준이 제공하는 전체 정책금리 XML 파일 | IORB 계열 `RESBM_N.D`를 **2021-07-29**부터 실제 적용일 기준으로 반영 |
| **Standing Repo 상설 레포** | **2021-07-28**부터 최신 공개 거래일까지 | 현재 v3와의 호환을 위해 **2021-07-28의 기존 익일물 레포 값 0**을 보존한다. 상설 제도 적용일은 **2021-07-29**다. 동일 거래일의 유효한 결과를 합산하고 시험성 거래는 제외한다. |

발표일, 관측일, 금리 적용일을 구분한다. 값이 없는 날은 `null`로 유지하고 실제 `0`과 구분한다. 수요일 값이 없을 때 다른 날짜의 값으로 채우지 않는다. [현재 수집·정리 코드](../scripts/ingest.py#L200) · [상설 레포 도입 공지](https://www.newyorkfed.org/markets/opolicy/operating_policy_210728)

## 2. 변경 여부 판단

1. 6개 원천을 받아 현재 v3와 같은 구조의 **화면용 JSON 한 벌**을 만든다. 주간 이력과 일간 이력, 관측일·발표일, 화면에 표시하는 출처 정보를 포함한다.
2. 새 결과를 **현재 운영 중인 버전**과 비교한다. 신규 관측치 추가, 과거 수치 정정, 값의 추가·삭제, 화면에 표시되는 기준일 변경은 모두 갱신 사유다.
3. **실행할 때마다 달라지는 수집 시각, 임시 파일 경로, JSON의 줄바꿈이나 항목 순서**는 변경 판단에서 제외한다. 수집 시각만 바뀌었다면 기존 버전을 유지한다. 일일 작업의 성공·실패와 확인 시각은 별도 운영 기록에 남긴다.
4. 다운로드 실패, 자료 형식 오류, 예상치 못한 과거 구간 누락이 있으면 새 버전 전환을 보류한다. 휴장으로 새 자료가 없는 정상 상황과 수집 실패를 구분한다.

## 3. 검증과 저장의 역할

**수집 프로그램**이 원천 파일의 다운로드 성공 여부, 자료 형식, 날짜별 누락, 계산 결과와 최종 JSON을 검증한다. 새 JSON을 조각으로 나누고, DB에 저장한 조각을 다시 읽어 원본과 일치하는지도 수집 프로그램이 확인한다. **Altibase는 전달받은 값의 저장과 조회만 담당한다.** DB 안에 JSON 분석이나 파일 검증 기능을 만들 필요는 없다.

검증을 통과한 새 버전만 화면에 공개한다. 수집 또는 검증에 실패하면 이전 버전을 계속 제공하고, 실패 내용은 수집 프로그램의 운영 기록에 남긴다.

## 4. Altibase 테이블과 칼럼

테이블은 세 개다. 아래 자료형은 설계 예시이며, 회사에서 쓰는 Altibase 버전과 문자셋에 맞춰 동일한 저장 용량을 확보한다. `snapshot_id`에는 화면을 구분하는 고정값 `FED_BALANCE_SHEET_V3`를 사용한다. `version_id`는 JSON 한 벌을 식별하는 고유 번호다.

### JSON 버전 테이블 `FED_SNAPSHOT_VERSION`

| 칼럼 | 자료형 예시 | 저장할 값 |
|---|---|---|
| `version_id` | `VARCHAR(36)` | 버전별 고유 ID. 기본키 |
| `snapshot_id` | `VARCHAR(32)` | `FED_BALANCE_SHEET_V3` |
| `created_at_utc` | `VARCHAR(20)` | 생성 시각. 예: `2026-11-04T00:00:00Z` |
| `chunk_count` | `INTEGER` | 이 버전의 조각 개수 |
| `json_byte_count` | `BIGINT` | 완성된 JSON의 UTF-8 바이트 길이 |
| `sha256_hex` | `VARCHAR(64)` | 완성된 JSON의 SHA-256 값. 수집 프로그램의 비교·검증용 |

### JSON 조각 테이블 `FED_SNAPSHOT_CHUNK`

| 칼럼 | 자료형 예시 | 저장할 값 |
|---|---|---|
| `version_id` | `VARCHAR(36)` | 해당 조각이 속한 버전 ID |
| `chunk_no` | `INTEGER` | 1부터 시작하는 조각 순번 |
| `chunk_text` | `VARCHAR(4000)` | JSON의 일부. 실제 저장 크기 4,000바이트 이하 |

`version_id`와 `chunk_no`의 조합을 기본키로 지정한다. 수집 프로그램은 JSON 문자를 순서대로 나누고, 회사 DB 문자셋에서 각 `chunk_text`의 실제 저장 바이트 길이가 4,000 이하인지 확인한다. 한글 등 문자의 중간을 자르지 않는다. 여유를 두기 위해 3,000바이트 안팎으로 나누어도 된다.

### 현재 제공 버전 테이블 `FED_SNAPSHOT_CURRENT`

| 칼럼 | 자료형 예시 | 저장할 값 |
|---|---|---|
| `snapshot_id` | `VARCHAR(32)` | `FED_BALANCE_SHEET_V3`. 기본키 |
| `version_id` | `VARCHAR(36)` | 현재 화면에 제공하는 버전 ID |

이 테이블에는 해당 화면에 대해 한 행만 둔다. 웹서버는 여기서 `version_id`를 **한 번 읽은 뒤**, 그 번호에 속한 조각만 `chunk_no` 순서로 조회해 합친다. 완성된 JSON을 `/api/h41`에서 반환한다. [현재 화면의 데이터 요청 코드](../assets/data.js#L55)

## 5. 새 버전으로 교체하는 순서

1. 수집 프로그램이 원천 자료와 완성된 JSON을 검증하고, 운영 중인 JSON의 화면 데이터와 비교한다. 달라진 내용이 없으면 저장을 끝낸다.
2. 내용이 바뀌었으면 새 `version_id`를 만들고, 버전 정보와 모든 조각을 **현재 제공 버전과 별도로** 저장한다.
3. 수집 프로그램이 저장된 조각을 순서대로 읽어 개수, 합친 길이, SHA-256 값, JSON 형식을 원본과 대조한다.
4. 대조에 성공한 경우에만 `FED_SNAPSHOT_CURRENT.version_id`를 새 번호로 변경한다. 이 한 행의 변경은 하나의 DB 트랜잭션으로 완료한다. 저장이나 대조가 실패하면 제공 버전을 변경하지 않는다.
5. 직전 정상 버전은 되돌리기에 쓸 수 있도록 보관한다. 오래된 버전의 삭제는 현재 제공 버전을 확인한 뒤 수집 프로그램이 수행한다.

화면의 **새로고침** 버튼은 회사 서버에 반영된 최신 버전을 다시 읽도록 연결한다. 원천 수집은 오전 7시 15분 예약 작업에서 수행한다.

## 6. 개발 완료 확인 기준

- **초기 적재**에서 v3의 주간 시작일이 `2013-09-25`이고, SOFR·EFFR·IORB가 명세의 날짜부터 표시된다. IORB가 없는 기간에는 IORB와의 금리 차이도 비어 있다.
- **기존 화면과 기간이 겹치는 구간**에서 순유동성, 1·4·13주 변화, 일간 금리, 결측 표시가 일치한다.
- **같은 자료로 두 번 실행**하면 두 번째에는 Altibase의 제공 버전이 바뀌지 않는다. **과거 수치 한 건만 정정**해도 새 버전이 만들어지고 화면에 정정값이 표시된다.
- **4,000바이트 경계에 한글이 있는 JSON**을 저장했다가 합쳐도 원본과 일치한다.
- **수집 실패, 조각 누락, 저장 도중 중단**을 각각 재현해도 화면에는 직전 정상 버전이 표시된다.
- **DB 자체에는 검증 절차가 없다.** 검증 실패 시 수집 프로그램이 제공 버전을 전환하지 않는지 확인한다.
