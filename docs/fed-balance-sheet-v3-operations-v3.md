# FedBalanceSheet v3 운영 명세 — 개정 3

2026-11-25. 화면 버전은 v3이며 문서 개정 번호는 3이다. 기존 명세와 개정 2는 보존한다. DB 조회 담당자가 SELECT만 수행하는 조건으로 개정 2의 화면 데이터 생성·전달 절차를 이 문서로 대체한다. DB 연동과 화면 어댑터는 아직 구현되지 않았다.

## 데이터 흐름

입수 프로그램 → 여섯 원천 해석·결합·계산·검증 → 완성된 화면 JSON → 문자열 조각 DB 저장 → 정렬 SELECT → 화면에서 문자열 연결·JSON 해석 → 기존 표·차트.

원천별 여섯 테이블의 key와 FED-TEXT-2 규격은 [개정 2](fed-balance-sheet-v3-operations-v2.md)의 테이블·text·분할 규칙을 유지한다. 이 테이블들은 원천별 확인용이다. 화면은 아래 화면용 테이블만 조회한다. DB 조회 담당자는 원천 복원·단위 변환·날짜 결합·금융 계산·JSON 생성·HTTP 서버 개발을 맡지 않는다.

## 입수 프로그램 책임

매일 07:15 KST에 기존 수집 범위 전체를 재수집한다. 기존 운영 명세 개정 2의 수집 범위·원천 필터·휴장·결측 기준은 유지한다. `scripts/ingest.py`의 run/normalize/normalize_funding_daily/validate에 해당하는 처리로 완성된 화면 데이터를 만든다. 단위 변환, 레포 거래별 중복 제거와 날짜별 합산, 수요일 결합, 순유동성·금리차 계산, 합계 대사 모두 입수 단계에서 완료한다.

화면 데이터의 최상위 필드는 meta/history/fundingDaily/quality/provenance다. 기존 latest.json과 assets/data.js의 validateSnapshot 계약을 유지한다. 실제 배포 응답에는 임시 원본 파일 경로를 넣지 않고 출처 URL과 처리 기준을 제공한다. 브라우저에서 선택 기간의 1/4/13주 변화 등을 계산하는 기존 기능은 계속 재사용한다.

완성된 JSON 문자열은 DB의 JSON 자료형에 저장하지 않는다. 일반 문자열 컬럼에 분할 저장한다. JSON 생성은 입수 프로그램, 해석은 화면 프로그램이 맡으며 DB는 문자열만 저장·조회한다.

## 추가 테이블 FED_SCREEN_DATA

현재 화면 하나의 최신 완성 자료만 저장한다. load_id와 과거 버전 이력은 두지 않는다.

| 컬럼 | 논리 자료형/제약 | 의미 |
|---|---|---|
| group_no | 양의 정수 | key1. 7조각씩 묶는 순번 |
| chunk_no | 정수 1~7 | 묶음 안의 조각 번호 |
| chunk_text | 문자열, 실제 저장 2,000바이트 이하 | 완성 JSON의 일부 |
| total_chunks | 양의 정수 | 전체 JSON의 조각 수. 모든 행에 동일하게 저장 |
| payload_sha256 | 64자리 ASCII 문자열 | 완성 JSON을 UTF-8로 인코딩한 SHA-256. 모든 행에 동일하게 저장 |

기본키는 (group_no, chunk_no)다. total_chunks와 payload_sha256는 번호 중간뿐 아니라 마지막 조각 누락·다른 자료 혼입도 확인하기 위한 값이다. 같은 완성 자료에 대해 모든 행에서 동일해야 한다. 실제 DDL은 DB 담당자가 사내 Altibase와 문자셋에 맞춰 확정한다.

입수 프로그램은 문자 경계를 보존하면서 DB 문자셋 기준 조각당 2,000바이트 이하로 분할한다. 연속 조각 7개씩 group_no를 올리고 chunk_no는 1부터 다시 시작한다. 실제 14,000바이트 용량은 문자 경계 때문에 일부 남을 수 있다. 모든 조각을 연결한 문자열은 분할 전과 정확히 같아야 한다. 해시는 DB 저장 문자셋과 별개로 복원 문자열의 UTF-8 바이트에서 계산한다.

## 전체 교체

원천 6종과 화면용 데이터가 모두 검증된 뒤 임시 적재 영역에 준비한다. DB 재조회로 조각 수·바이트·해시·JSON·화면 검사를 수행하는 주체는 입수 프로그램이다. DB 조회 담당자의 업무 범위와 혼동하지 않는다.

DB 담당자는 원천 6개와 화면용 테이블을 하나의 일관된 교체 절차로 공개한다. 조회 중 구자료와 신자료가 섞이지 않는 트랜잭션/격리 수준을 검증한다. 보장이 어렵다면 교체 동안 조회를 일시 중단한다. TRUNCATE/DDL의 원자성을 가정하지 않는다. 실패 시 운영 자료를 유지하고, 성공 후 진행 중 조회가 끝나면 이전 임시 자료를 삭제한다. 장기 원본·과거 버전 보관은 하지 않는다.

## SELECT 계약

```sql
SELECT group_no, chunk_no, chunk_text, total_chunks, payload_sha256
FROM FED_SCREEN_DATA
ORDER BY group_no, chunk_no;
```

하나의 조회 결과 전체를 전달한다. 행 수 제한·페이지 잘림·문자열 trim·줄바꿈 변환을 적용하지 않는다. SQL에서 문자열을 합치거나 JSON을 분석하거나 금융 계산을 수행하지 않는다. 결과 전달은 회사의 기존 조회 통신 기능을 사용한다. 그 통신 기능과 화면 연결은 화면 담당자가 맡는다.

화면은 번호·행 수·해시 일치를 확인하고 순서대로 chunk_text를 구분자 없이 연결해 JSON.parse한다. 해당 객체를 기존 validateSnapshot에 통과시킨 뒤 표·차트를 갱신한다. 최초 조회 실패 시 오류 표시, 이후 갱신 실패 시 직전 정상 화면 유지. 조회 결과가 비었거나 일부만 오면 정상 데이터로 취급하지 않는다.

## 완료 기준

- SELECT 결과만으로 기존 화면 데이터 객체가 정확히 복원된다.
- 2,000바이트 다중바이트 경계, 그룹당 7조각, 다음 그룹으로 이동, 마지막/중간 조각 누락, 잘림과 혼입을 검사한다.
- 전체 이력의 기존 주간·일간 수치와 기간별 계산이 일치한다.
- 수집/적재/조회 실패 및 교체 중 조회에서 부분 자료가 화면에 노출되지 않는다.
