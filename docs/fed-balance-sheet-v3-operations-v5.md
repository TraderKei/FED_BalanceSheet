# FedBalanceSheet v3 운영 명세 — 개정 5

2026-11-25. 화면 버전은 v3이며 문서 개정 번호는 5다. 기존 명세와 개정 2·3·4는 보존한다. 회사 운영은 FED_SCREEN_DATA 하나만 저장하는 구성으로 확정한다. 이전 원천별 테이블 및 FED-TEXT-2 저장 설계는 이번 구현에서 사용하지 않는다. DB 연동과 화면 어댑터는 아직 구현되지 않았다.

## 데이터 흐름

입수 프로그램 → 여섯 원천 해석·결합·계산·검증 → 완성된 화면 JSON → 문자열 조각 DB 저장 → 정렬 SELECT → 화면에서 문자열 연결·JSON 해석 → 기존 표·차트.

원천별 6개 테이블은 만들지 않는다. 원천 파일은 입수 프로그램의 임시 작업 영역에서만 해석하고, 완성된 화면 데이터만 FED_SCREEN_DATA에 저장한다. DB 조회 담당자는 SELECT 결과 전달만 수행한다. 이 결정은 내부 프로그램이 여러 SELECT를 지원하는지와 무관하며, 자료 가공을 입수 단계에서 완료하기 위한 것이다.

## 입수 프로그램 책임

매일 07:15 KST에 기존 수집 범위 전체를 재수집한다. 아래 수집 범위와 원천 필터·휴장·결측 기준을 적용한다. `scripts/ingest.py`의 run/normalize/normalize_funding_daily/validate에 해당하는 처리로 완성된 화면 데이터를 만든다. 단위 변환, 레포 거래별 중복 제거와 날짜별 합산, 수요일 결합, 순유동성·금리차 계산, 합계 대사 모두 입수 단계에서 완료한다.

화면 데이터의 최상위 필드는 meta/history/fundingDaily/quality/provenance다. 기존 latest.json과 assets/data.js의 validateSnapshot 계약을 유지한다. 실제 배포 응답에는 임시 원본 파일 경로를 넣지 않고 출처 URL과 처리 기준을 제공한다. 브라우저에서 선택 기간의 1/4/13주 변화 등을 계산하는 기존 기능은 계속 재사용한다.

완성된 JSON 문자열은 DB의 JSON 자료형에 저장하지 않는다. 일반 문자열 컬럼에 분할 저장한다. JSON 생성은 입수 프로그램, 해석은 화면 프로그램이 맡으며 DB는 문자열만 저장·조회한다.

## 유일한 운영 데이터 테이블 FED_SCREEN_DATA

현재 화면 하나의 최신 완성 자료만 저장한다. load_id와 과거 버전 이력은 두지 않는다.

| 컬럼 | 논리 자료형/제약 | 의미 |
|---|---|---|
| group_no | 양의 정수 | key1. 7조각씩 묶는 순번 |
| chunk_no | 정수 1~7 | 묶음 안의 조각 번호 |
| chunk_text | 문자열, 실제 저장 2,000바이트 이하 | 완성 JSON의 일부 |
| total_chunks | 양의 정수 | 전체 JSON의 조각 수. 모든 행에 동일하게 저장 |

기본키는 (group_no, chunk_no)다. total_chunks는 마지막 조각을 포함한 전체 조각 수를 확인하기 위한 값이며 모든 행에서 동일해야 한다. payload_sha256 컬럼과 해시 생성·대조는 사용하지 않는다. 실제 DDL은 DB 담당자가 사내 Altibase와 문자셋에 맞춰 확정한다.

입수 프로그램은 문자 경계를 보존하면서 DB 문자셋 기준 조각당 2,000바이트 이하로 분할한다. 연속 조각 7개씩 group_no를 올리고 chunk_no는 1부터 다시 시작한다. 실제 14,000바이트 용량은 문자 경계 때문에 일부 남을 수 있다. 모든 조각을 연결한 문자열은 분할 전과 정확히 같아야 한다. 입수 프로그램은 적재 전 문자열과 DB에서 복원한 문자열을 직접 비교한다.

## 전체 교체

원천 6종의 해석과 완성 화면 데이터 검증을 마친 뒤, 화면용 조각만 임시 적재 영역에 준비한다. 임시 영역은 교체용이며 별도의 영구 원천 테이블이 아니다. DB 재조회로 조각 수·바이트·원문 직접 대조·JSON·화면 검사를 수행하는 주체는 입수 프로그램이다. DB 조회 담당자의 업무 범위와 혼동하지 않는다.

DB 담당자는 FED_SCREEN_DATA의 전체 행을 하나의 일관된 교체 절차로 공개한다. 조회 중 구자료와 신자료가 섞이지 않는 트랜잭션/격리 수준을 검증한다. 보장이 어렵다면 교체 동안 조회를 일시 중단한다. TRUNCATE/DDL의 원자성을 가정하지 않는다. 실패 시 운영 자료를 유지하고, 성공 후 진행 중 조회가 끝나면 이전 임시 자료를 삭제한다. 장기 원본·과거 버전 보관은 하지 않는다.

## SELECT 계약

```sql
SELECT group_no, chunk_no, chunk_text, total_chunks
FROM FED_SCREEN_DATA
ORDER BY group_no, chunk_no;
```

위 SELECT는 기본 조회 예시이며 내부 프로그램의 조회 횟수를 제한하는 규정은 아니다. 화면용 자료의 전체 행이 빠짐없이 전달되어야 한다. 여러 조회로 나눌 경우 교체 중 자료가 섞이지 않도록 동일한 일관된 읽기를 보장하고 전체 결과의 조각 수와 순서를 검증한다. 행 수 제한·페이지 잘림·문자열 trim·줄바꿈 변환을 적용하지 않는다. SQL에서 문자열을 합치거나 JSON을 분석하거나 금융 계산을 수행하지 않는다. 결과 전달은 회사의 기존 조회 통신 기능을 사용한다. 그 통신 기능과 화면 연결은 화면 담당자가 맡는다.

화면은 번호·행 수 일치를 확인하고 순서대로 chunk_text를 구분자 없이 연결해 JSON.parse한다. 해당 객체를 기존 validateSnapshot에 통과시킨 뒤 표·차트를 갱신한다. 최초 조회 실패 시 오류 표시, 이후 갱신 실패 시 직전 정상 화면 유지. 조회 결과가 비었거나 일부만 오면 정상 데이터로 취급하지 않는다.

## 완료 기준

- SELECT 결과만으로 기존 화면 데이터 객체가 정확히 복원된다.
- 2,000바이트 다중바이트 경계, 그룹당 7조각, 다음 그룹으로 이동, 마지막/중간 조각 누락, 순서 오류, 중복 및 JSON 형식 오류를 검사한다.
- 전체 이력의 기존 주간·일간 수치와 기간별 계산이 일치한다.
- 수집/적재/조회 실패 및 교체 중 조회에서 부분 자료가 화면에 노출되지 않는다.
- 샘플과 검사: [구현 인계 명세 개정 5](v3-implementation-handoff-v5.md).

| ON RRP | 2013-09-23부터 최신 공개일까지 | Reverse Repo·Overnight·Results, 거래 ID 중복 제거 후 같은 날짜 합산 |

정확한 URL·원천 계열·필터는 scripts/ingest.py가 기준이다. 휴장·미발표일에 없는 값을 0이나 전일 값으로 채우지 않는다. 최신 주간 필수 입력 누락·파싱 실패·합계 대사 실패 시 새 자료 공개를 보류한다. 정상 휴장과 예상 밖 누락의 운영 판정은 별도 구현 대상이다. 수집 시각만 바뀐 경우를 제외하고 화면 값·날짜·출처의 의미 있는 변경 여부를 비교하여 교체할 수 있다.

원본과 이전 완성 자료를 장기 보관하지 않는다. 매번 새 임시 파일로 수집하고 검증된 자료의 교체 완료 후 임시 파일을 정리한다. 실패 시에도 운영 DB의 이전 정상 결과는 유지한다. 작업 성공/실패·건수·검사 결과는 운영 로그로 남기되 원본 파일 보관과 구분한다.

## 해시 제외에 따른 검증 범위

테이블 컬럼은 group_no, chunk_no, chunk_text, total_chunks 네 개다. 화면에서는 조각 번호·전체 개수·중복·순서, JSON.parse 및 validateSnapshot 검사를 유지한다. 이 검사만으로 모든 내용 변경이나 같은 조각 수의 신구 자료 혼입을 탐지할 수는 없다. 이를 검출한다고 가정하지 않고, 입수 단계의 원문 직접 대조와 DB의 일관된 전체 교체·조회로 정상 전달을 보장한다. 기존 원천 다운로드 코드의 내부 체크섬 사용과 별개로, 화면 테이블·전달 계약에는 해시가 없다.
